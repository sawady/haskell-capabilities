Capabilities in the type

The thesis needs a program's type to say which resources it may use: the network, files, the console. With that, an oracle can reject whatever was not granted while a language model writes the code. This page compares four ways of achieving it in Haskell, with the same problem in all of them: download a page and print its first line.

All the code on this page comes from the repository sawady/haskell-capabilities and compiles with GHC 9.12.2. The errors shown are the ones GHC gives.

Reading order

The sections follow the order in which the files are best read. Each one builds on the previous ones and needs, in addition, what is listed here:

  • 1. Types only, src/A_TypesOnly.hs: IO and do notation, records, a constraint such as Monad m =>.
  • 2. Tagless final, src/Capabilities.hs, src/B_TaglessFinal.hs and the three must-fail/B_*.hs: type classes and instances; Functor, Applicative and Monad instances for a newtype; the State monad.
  • 3. Monad transformers, src/C1_Transformers.hs and then src/C2_Mtl.hs: ReaderT, StateT and lift; for the mtl style, the classes MonadReader and MonadState.
  • 4. Effect rows, src/D_EffectRows.hs (the program), then src/Effects.hs (the mechanism) and must-fail/D_EffectNotInRow.hs: GADTs, DataKinds (type-level lists), multi-parameter classes and overlapping instances.

Type classes, monads and monad transformers are explained in the Typeclassopedia and in the documentation of transformers and mtl. The extensions of section 4 are in the GHC User's Guide: GADTs, DataKinds, multi-parameter classes and overlapping instances.

The starting point: IO allows everything

In Haskell, the type IO () says that the function does input and output, but not which. This version, besides downloading the page, reads the process's environment variables, and its type does not change.

This is called ambient authority: the code can do anything the process can do, without anyone having granted it. The four approaches that follow try to remove it.

1. Types only: capabilities as arguments

The most direct way is to pass each capability as a value: a record with the functions that implement it. If the result is still IO, the type names the capabilities but does not enforce them. The important change is to make the monad abstract:

Since the function does not know what m is, it can only do what the records give it. This is plain Haskell 2010 and it already solves the safety problem. What it does not give is convenience: each capability is passed by hand in every call, and a function's type lists the records in a fixed order.

2. Tagless final: capabilities as type classes

Instead of passing records, each capability is a single-parameter type class. A function that needs the network asks for Net m, and the compiler finds the implementation.

Neither function has a signature, and GHC infers exactly the capabilities each one uses:

This is what matters most to the thesis. The set of capabilities a fragment uses comes out of type inference, which is decidable in Haskell 2010. The oracle only has to compare that set with the grant.

The interpreter is a concrete monad with instances for some capabilities. Choosing the interpreter is choosing what is granted. There is one over IO and a pure one for testing, and the same program runs in both without changes.

What GHC rejects

GHC’s messages are long, but they all have the same shape. The first one is shown whole and read part by part; the others, only up to where they say something new. The complete messages are in outputs/must-fail-*.txt.

How to read it, from top to bottom:

  • must-fail/B_CapabilityNotGranted.hs:12:13: error: [GHC-39999]: the file, the line (12) and the column (13) where GHC found the problem, and the code of the error. The code says which kind of error it is, and can be looked up in the Haskell Error Index; GHC-39999 is a missing instance.
  • Each • starts a part of the message. The first part is the error; the other ones say where it happened.
  • Could not deduce ‘Files m’ arising from a use of ‘readTextFile’: using readTextFile requires the constraint Files m, and GHC could not obtain it. It says “deduce” because m is abstract: GHC can only use what the signature gives it.
  • from the context: (Net m, Console m): what the signature gives. Read together with the previous line, this is the capability check: the body needs Files and the signature only grants Net and Console.
  • bound by the type signature for: summary :: forall (m :: * -> *). … and at …:9:1-44: where that context comes from, the signature on line 9. GHC writes the signature with its type variable made explicit: forall (m :: * -> *) means “for every m that takes a type and gives a type”, such as IO or Test. * is an older name for Type.
  • Possible fix: add (Files m) to the context: GHC’s suggestion is to grant the capability in the signature. The program would compile, with one more capability: whether to grant it is a decision about the signature, not a correction of the body.
  • In a stmt of a 'do' block, In the expression, In an equation for ‘summary’: where the error is, from the inside out: the statement, the do block that contains it, the equation that contains the block. The first one is usually enough.
  • The last lines quote line 12 and mark with ^^^^ the expression the error is about: readTextFile, at column 13.
  • Couldn't match type ‘m’ with ‘IO’: two types that had to be the same are not. The code, GHC-25897, is not the one of the previous error: this is not a missing capability, but a type that does not fit.
  • Expected: m () and Actual: IO (): “expected” is what the place demands, because every statement of a do block of type m () has to be an action in m; “actual” is what the expression is, because putStrLn gives an IO ().
  • ‘m’ is a rigid type variable bound by the type signature: “rigid” means that the body cannot choose m. Whoever calls summary chooses it, so the body cannot assume that it is IO. This is the abstract monad at work.
  • The rest of the message, not shown here, has the same In a stmt of a 'do' block lines as before, and Relevant bindings include, which lists the variables in scope with their types, in case one of them explains the error.
  • No instance for ‘Files App’: the same code as the first error, GHC-39999, with other words. There the type was a variable, m, and GHC looked for the capability in the context. Here it is a concrete type, App, and GHC looked for an instance, which does not exist.
  • arising from a use of ‘summaryWithFile’ and 35:16: the error is reported where the program is run with App, on line 35, and not in summaryWithFile, which is correct. What fails is the choice of interpreter.

Why classes and not just types?

Records over an abstract monad (section 1) already give the same safety. The difference is in who does the work:

Records of functionsType classes
Who passes the capabilitiesThe programmer, as arguments, in every callThe compiler, through instance resolution
Which capabilities a function usesThe ones it receives; they have to be declaredGHC infers them
How they combineA list of arguments, in orderA set of constraints, unordered
Two implementations at onceYes, by passing two different recordsOne per monad; for another, another interpreter
For a model that generates codeIt has to carry the records through the whole programIt writes the code directly; the capabilities are deduced

For the thesis, the decisive row is the second one. With classes, the set of capabilities of a half-written program comes out of inference. With records, the oracle would have to track which arguments are used, which is also possible but is work of its own.

3. Monad transformers

This is the line of work of the UNQ research group the thesis belongs to. Each layer of the stack provides a capability, and the type names the concrete stack, in a fixed order.

The example shows two things. Using an inner layer means lifting by hand with lift, as many times as there are layers above it. And since IO is at the bottom of the stack, lift (lift ...) reaches any IO operation: transformers put the capabilities in order, but they do not remove ambient authority.

The mtl style is tagless final

The mtl classes, such as MonadReader and MonadState, are exactly the idea of section 2: MonadReader Config m means "m can read a Config". The difference is that they have two parameters, so they require extensions.

A capability of our own, such as Net, lives alongside the mtl ones. For it to go through the stack it takes one instance per transformer, which is known as the n² instances problem:

The consequence for the thesis: there is no need to choose between tagless final and transformers. Programs are written with capabilities as classes, and interpreters are built with transformer stacks, as in this example. What has to be avoided is MonadIO, which gives back the full ambient authority.

4. Effect systems with rows

Here the computation carries a row in its type: the list of effects it may use. Eff es a is a computation that produces an a using the effects in es. The function below is polymorphic in the row: it works in any row that contains Net and Console. That is row polymorphism.

Effects only declare operations. What they do is decided by a handler, which removes one effect from the row and interprets it. When the row is empty, the computation is pure.

The same program is run by applying the handlers in order. One interprets the console by collecting lines in a list, without IO. Another interprets it with real IO, which then has to be further down the row. Rejecting a capability that was not granted works just as with classes:

  • The same shape as the first error in section 2: Could not deduce ‘Member Console es’, from the context: Member Net es. The body needs Console to be in the row, and the signature only says that Net is.
  • forall (es :: [* -> *]): es is a type-level list whose elements take a type and give a type, like Net and Console. That list is the row.
  • The signature is split over three lines only because it is longer; it is the one on line 9.

In Haskell the row is a type-level list, which is why DataKinds, GADTs, TypeOperators and four other extensions are needed. A list has an order and can repeat elements, which a real row does not. Languages designed for this, such as Koka, write the row in the function's type, with a variable for "the rest of the effects", and treat it as a set. In Haskell, libraries such as effectful, polysemy and fused-effects provide it. The repository uses a minimal version, written by hand in about 120 lines, so that the mechanism can be seen without dependencies.

In GHCi, ghci -isrc src/D_EffectRows.hs shows how each handler removes one effect from the row. Applying them in the other order is a good way to check the explanation:

The hand-made Effects is a minimal version of what the libraries do. This is example D written with effectful-core, the core of effectful. The effects only declare operations, as before; the differences are in the details:

Net :> es is what Member Net es was: Net is in the row. Each effect has one more parameter, the monad m, for operations that take computations as arguments (these two do not), and declares how it is dispatched: Dynamic means that a handler decides what each operation does. The program, summary, is the same as in D with :> in its signature.

The handlers still remove one effect from the row, but they do not walk through the computation by hand: interpret receives what to do with each operation. The pure console uses another effect of the library, a Writer, which reinterpret adds and removes. IO is an effect of the library too, IOE, in the place of EmbedIO, and runPureEff and runEff do what run and runIO did. It prints the same as D, with IOE instead of EmbedIO:

What it costs: a dependency, effectful-core, which also brings in packages that do not ship with GHC (monad-control, primitive, strict-mutable-base, transformers-base, unliftio-core), and six extensions: DataKinds, GADTs, TypeOperators and FlexibleContexts, as in Effects, plus TypeFamilies for DispatchOf and LambdaCase for the \case of the handlers. It is the only part of the repository that needs cabal: bridge/effectful/ is kept apart, ./build.sh does not use it, and a CI workflow of its own builds it with effectful-core 2.7.1.2 and GHC 9.12.2 and compares its output.

What suits the thesis

  1. Write the programs in tagless final, with single-parameter classes. It is Haskell 2010 with no extensions, inference is decidable and GHC computes the set of capabilities of each fragment. That is what the oracle needs.
  2. Build the interpreters with transformers. It is the existing line of work of the UNQ research group and it fits without conflict, as the mtl example shows.
  3. Leave out of the subset everything that gives back ambient authority: IO in signatures, MonadIO and unsafePerformIO. Otherwise the capabilities can be bypassed.
  4. Use effect rows as a point of comparison in the theoretical framework. They are more expressive, because a handler can reinterpret an effect, but they require extensions and a more complex type system for the oracle.

One limitation to keep in mind: with classes, the capability is "use the network", not "use this URL". Restricting which resources are accessed would call for refinements or other mechanisms, and is outside this scope.

The holes, compiling

Point 3 of the previous section says that MonadIO and unsafePerformIO give back ambient authority. These two programs, in escapes/, show it: both compile, with the capabilities of section 2, and both read the environment, as the first program of this page did.

With MonadIO m in the constraints, liftIO runs any IO action. At least the escape is in the type, where it can be seen.

This one has exactly the type of summary in section 2, and nothing in it shows that the environment is read: unsafePerformIO runs an IO action as if it were a pure value.

GHC already has a mechanism to leave such functions out of the language: Safe Haskell. A module that starts with {-# LANGUAGE Safe #-} can only import modules that Safe Haskell trusts, and System.IO.Unsafe is not one of them. The User’s Guide gives it this use: its example is a restricted IO monad for untrusted code, and it names capability-based security among the systems that can be built as a library with it. The same program, in a Safe module, does not compile:

The error, GHC-44360, is at the import, on line 11: in a Safe module, System.IO.Unsafe cannot even be imported. MonadIO, on the other hand, is not affected: escapes/MonadIO.hs is itself a Safe module, because liftIO comes from a module that Safe Haskell trusts, and doing IO is not what Safe Haskell forbids. So the two holes are closed in different ways: unsafePerformIO, with Safe Haskell; MonadIO, like IO in signatures, by leaving it out of the subset.

Exercises

The repository has six graded exercises, from section 1 to section 4: adding a capability as a record and as a class, predicting GHC’s errors with transformers and in the mtl style, running the mtl-style program without IO, following the row through the handlers, and adding the same capability in the four styles to compare what each one costs. The solutions are apart from the statements, and ./build.sh checks them like the examples.

For teachers, the teaching guide has learning objectives for each section, an estimated duration for each section and exercise, and how to use the exercises in class.
